# C27 — Prepare and validate 0.8.0 release artifacts

## Goal

From the promoted C30 code candidate revision, assemble the exact tested Linux, macOS,
and Windows wheels plus a source distribution, verify package metadata and
checksums, and create a local-only `v0.8.0` tag candidate. C28 publishes.

## Acceptance

- Use the promoted C30 implementation candidate SHA recorded by its green
  native workflow run; confirm that commit is reachable from `origin/main`.
- Download that exact workflow run’s artifacts and confirm each artifact name
  includes its source SHA and platform, with exactly one tested wheel per
  Linux/macOS/Windows job.
- Tag the exact C30 implementation candidate SHA. If a later C30 docs-only
  closeout commit is on `origin/main`, verify the package input tree at the
  candidate SHA matches the promoted tree for all release inputs (Cargo files,
  Rust/Python sources, build scripts, license, and package metadata).
- Build the 0.8.0 sdist from that same commit.
- Verify every wheel and the sdist reports version 0.8.0; wheel platform tags
  match Linux/macOS/Windows and sdist contents match the release source.
- Generate SHA-256 checksums for every file and independently recompute each
  digest.
- Check PyPI, GitHub Release, and `git ls-remote origin refs/tags/v0.8.0`
  for existing 0.8.0 collisions before creating a release candidate.
- Create and verify local-only tag `v0.8.0` at the promoted C30 source SHA; do
  not push the tag or upload artifacts in this card.
- Run `cargo test --workspace`, build the sdist, verify wheel/sdist metadata,
  platform tags, provenance and checksum counts; obtain independent code↔card
  and tests↔card reviews.
- Write and review a postmortem; promote green coherent commits
  worktree branch → local `main` → `origin/main`.
