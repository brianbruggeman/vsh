## Design evidence

`CreateOptions` and `EnterOptions` are justified because they are distinct,
serializable operation inputs shared across the Rust library, CLI and future
PyO3 adapter. No extra wrapper type is introduced. The environment constructor
seeds `Default::default()` before `.env()`, so unset variables preserve the
single Rust default implementation. `#[serde(default)]` calls that same
implementation for omitted fields. `Settings` has no per-field defaults here
because env resolution always starts from the seeded value. The `Validate`
derive currently enforces no additional constraints, but keeps the options on
the same validated construction seam as `Config` for future constrained values.

The incumbent CLI defaults symlinks on every platform (`--copy` inverses the
setting) and pip on (`--no-pip` inverses it). Platform-specific filesystem
behavior remains in later platform/effect cards; this card records portable
intent only.

## Postmortem

The initial test let only explicit false environment overrides exercise the
create settings, so it did not prove that the seeded true defaults survive an
unset environment. Add a scoped unset-env assertion whenever the intended
behavior is a default. Exercise every public construction path for both option
types, even when the constructors share the same implementation pattern. Also
type annotate `None` in `temp_env::with_vars` because its generic value type is
ambiguous. The strengthened test now has that default proof, both fluent paths,
and serde defaults. This review feedback is incorporated before promotion.
