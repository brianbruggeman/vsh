# C20 — Allocation, copy, and lock audit

## Acceptance

- Record process allocation events and peak RSS for Rust and legacy Python
  startup with commands, tool, platform, and machine-load provenance; if host
  load cannot be collected, narrow the claim and record the limitation.
- Run the reusable cold-start benchmark with `N>0`, recording throughput,
  single-request latency, p50/p90/p99/max, CPU%, peak RSS, errors, and CoV.
- Inventory copy/ownership boundaries and lock-bearing code paths. State what
  was measured and what could not be attributed to VSH code.
- Keep the benchmark reproducible, run its validation, review the result
  against this card twice, add a postmortem, and land green through branch →
  local `main` → `origin/main`.

## Design

`scripts/c20_cold_start.py` is a standard-library-only Unix runner: it starts
each command as a new process with `fork`/`exec`, obtains child CPU and maximum
RSS from `wait4`, and records one-request latency for every sample. It does not
flush the OS page cache, so this measures new-process CLI startup under a warm
filesystem cache. No benchmark dependency or product type was added.

The allocator event profile uses macOS `MallocStackLogging=1` and
`malloc_history -allEvents`. `scripts/c20_alloc_capture.py` builds a temporary
exit-delay dylib, captures each process's allocator log while it waits at
exit, and records the host load before process launch and after each capture. The
exact event logs are compressed in `evidence/`; summary counts include dyld,
libc, and runtime allocations as well as VSH. They are process totals, not
VSH-only attribution.

## Findings

The run compares `/tmp/cargo_target/release/vsh --version` against
`python3 -m vsh --version` from the legacy source package (version 0.7.1), on
macOS 15.8 arm64 with Python 3.14.6. Five process launches per command exited
successfully. The three saved runs recorded Rust CoVs of 158.93%, 10.61%, and
40.36%, and Python CoVs of 8.47%, 13.34%, and 30.09%. Every run exceeds the
5% stability threshold for both commands, so its latency and throughput are
measurements, not a performance verdict. Run 01 host load average was
84.23 / 68.58 / 66.85 on 10 CPUs; each run retains its own machine/load data.

The allocator event process totals and run-01 uninstrumented peak RSS were:

| Command | Allocation events | Requested bytes | Peak RSS | Errors |
|---|---:|---:|---:|---:|
| Rust `vsh --version` | 181 | 595,250 | 1,769,472 B | 0/5 |
| Python `vsh --version` | 4,685 | 14,514,805 | 33,849,344 B | 0/5 |

The allocator event counts include system/runtime work from `MallocStackLogging`
and dyld; they do not prove per-VSH allocation counts. The benchmark's peak RSS
uses the uninstrumented runs and is the memory comparison for this workload.

The source ownership scan found argument and environment collection into
`Vec<OsString>`/`Vec<(OsString, OsString)>`, path/config clones across effect
pipes, and Python-boundary conversions to owned `String`/`Vec<String>`. These
are cold-path or OS/Python ownership boundaries in the audited call paths; this
card did not change them. No `Mutex` or `RwLock` is declared in VSH's own
production Rust source. The pinned Proxima telemetry path depends on
`parking_lot` and has mutex-protected recorder registry and stdout/stderr sink
state. `println!` also uses the standard library's synchronized output path.
Therefore the end-to-end CLI is not a zero-lock system; no runtime lock count
was established. Copy bytes/calls were not intercepted, so zero-copy is also
not established. These limitations remain explicit rather than inferred from
source appearance.

The `Allocations` Instruments template did not produce a usable recording: its
launched target remained stopped (`ps` state `T`) for 24 seconds and export
returned `Document Missing Template Error`. I switched to the reproducible
`malloc_history` event capture script:

```sh
python3 scripts/c20_alloc_capture.py
```

The script records the temporary dylib source, exact `cc` command, process
commands, `malloc_history` invocation, exit codes, platform, Python version,
and load before/after each allocation capture in
`evidence/C20-allocation-capture.json`. The first benchmark invocation also
exposed an argparse command-boundary bug; command inputs now use explicit
quoted strings. Neither failed attempt changed product code.

## Validation

`cargo build --release -p vsh-cli`, `cargo fmt --all -- --check`, and
`git diff --check`: all exit 0. Benchmark command:

```sh
python3 scripts/c20_cold_start.py --runs 5 \
  --output docs/cards/evidence/C20-cold-start.json \
  --rust-command '/tmp/cargo_target/release/vsh --version' \
  --python-command 'python3 -m vsh --version'
```

Each of the three saved benchmark runs processed N=5 per command with zero exit
errors. Commands and outputs are saved as
`evidence/C20-cold-start-run-01..03.{json,log}`; build/fmt/diff logs are
alongside them. The allocator capture processed one Rust and one Python
process; records, load provenance, and derived counts are in
`evidence/C20-*-malloc-history.txt.gz` and
`evidence/C20-allocation-capture.json` and
`evidence/C20-allocation-summary.json`. Script syntax was exercised by the
successful captures.

## Postmortem

All benchmark samples landed on a heavily loaded host; every saved run exceeded
5% CoV for Rust and Python. Report the variance and decline a speedup claim
rather than selecting favorable samples. Instruments suspended the launch
target and returned an unusable trace, so confirm a replacement tool on a
minimal repro before scheduling it again. Save the benchmark command and host
load with the result. Keep process-wide allocator totals clearly labeled:
they include loader/runtime allocations and cannot support a claim about
VSH-only allocations.
The first staging pass also omitted `.log` evidence because repository ignore
rules matched it; inspect staged files and force-add required evidence before
promotion.
